# Verify the self-hosted push path

`scripts/self-hosted/push-model/SelfHostedPush.tla` is a TLA+ model of the fork's replacement for T3 Connect's push relay. Each fleet host's `AgentAwarenessRelay` publishes thread activity to one `t3-push` process. `t3-push` merges every host's threads into the single Live Activity card, attaches alerts, and sends the card to APNs for one iPhone. When the phone has no card, it sends push notifications instead. The phone's two switches, Live Activities and notifications, give four modes, and the phone can re-register with new switches at any time. TLC checks every order of steps in a small fleet, with crashes, APNs errors and host timeouts.

`t3-push` lives in `apps/push`. The model is its design contract: the **Design choices** below are what the implementation must do, the **Open findings** are where the design does not yet hold a rule, and the coverage table maps each `t3-push` action to its code. Rows marked "to write" are design choices `apps/push` does not implement yet.

## The rules

| Rule                            | In plain words                                                                                                                                                                                                                                                                                                                          | Harm when it breaks                                                                           |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `PushKnowsTruth`                | Once everything settles, `t3-push` holds every host's current thread phase.                                                                                                                                                                                                                                                             | The card and every later alert are computed from a stale row until that thread changes again. |
| `CardShowsTruth`                | Once everything settles, a live card shows every host's current thread phase.                                                                                                                                                                                                                                                           | The lock screen says "Working" for an agent that finished, or misses one that needs input.    |
| `NoDuplicateAlert`              | The phone never buzzes for a row the card already showed in that phase.                                                                                                                                                                                                                                                                 | Double buzzes for one approval or one completion.                                             |
| `NoMissedAlert`                 | With notifications on, every move of a card row into "needs input/approval" or "done" buzzes, except on a resend after a `t3-push` crash or an APNs timeout left it unknown whether the first send arrived.                                                                                                                             | A finished or blocked agent goes unnoticed.                                                   |
| `NoMissedNotification`          | With notifications on, once everything settles, every change of a thread into "needs input/approval" or "done" that `t3-push` read has rung, as a card alert or a push notification. Exceptions: the card's first update (no baseline), a send a crash or APNs timeout left unknown, and a change replaced before any delivery read it. | A finished or blocked agent goes unnoticed, on either channel.                                |
| `NoDuplicateNotification`       | The phone never rings twice for one change of a thread's phase, on either channel.                                                                                                                                                                                                                                                      | The same approval or completion rings again.                                                  |
| `SilentWhenNotificationsOff`    | After `t3-push` stores "notifications off", nothing it sends rings.                                                                                                                                                                                                                                                                     | The phone buzzes after the user silenced it.                                                  |
| `CardEndsWhenLiveActivitiesOff` | Once everything settles with Live Activities off, the phone shows no card.                                                                                                                                                                                                                                                              | A card the user turned off stays on the lock screen.                                          |
| `OnlyEndWhenBothOff`            | With both switches off, `t3-push` sends nothing but a silent end of a leftover card.                                                                                                                                                                                                                                                    | A phone that opted out of everything still gets updates or buzzes.                            |

"Settles" means `Quiescent` in the spec: `t3-push` is up, nothing is queued or in flight, no host has a publish pending, the freshly-armed grace window has passed, and no idle sweep is due.

Alerts and notifications are at most once. After an ambiguous send, the alert may be lost but never repeated. That matches upstream's delivery-claim behavior; `NoMissedAlert` and `NoMissedNotification` state the exception rather than hiding it. `NoMissedAlert` compares each card update with what the card showed; `NoMissedNotification` follows what `t3-push` read, so it also sees alerts that went to a card the phone no longer shows. A change "replaced before a delivery read it" (input, then running again, both stored before the next delivery) owes nothing, as upstream's stale-state skip. Upstream's other exception, terminal freshness (a completion older than 2 minutes never rings), cannot happen here: the model has no clock, so every completion is fresh.

## Design choices the model requires

Each is a `CONSTANT` in the spec. `check.sh` turns each one off and confirms the rule it guards breaks.

| Choice                      | What `t3-push` or the host must do                                                                                                                                                                                                                                                                                                                                                                     | Breaks without it                                                                                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SerializeDelivery`         | One delivery at a time per device: read all rows, send, record. Coalesce publishes queued meanwhile into the next delivery.                                                                                                                                                                                                                                                                            | `NoMissedAlert` (two deliveries compare with the same baseline and land in either order)                                                                                                                                                                                           |
| `ReplyAfterDelivery`        | Answer a publish only after a delivery that read its row has been recorded. Answer per request, never per host: after a host timeout, the host's retry must not be answered by a delivery that read the rows before the retry was stored.                                                                                                                                                              | `NoMissedNotification` (a crash after "ok" loses the owed notification, which lives in memory, and the host never republishes)                                                                                                                                                     |
| `WriteAheadSend`            | Before each APNs card send, persist the aggregate being sent. Alerts compare with that persisted aggregate. The "unchanged aggregate" skip is off until the send is recorded.                                                                                                                                                                                                                          | `NoDuplicateAlert` (a crash or timeout after APNs accepted the send rings the same alert again)                                                                                                                                                                                    |
| `RetryForever`              | **Host-side fork patch.** `processThreadPublish` keeps retrying a failed publish (capped backoff) instead of giving up after `RELAY_AGENT_ACTIVITY_RETRY_DELAYS_MS` (about 31 s).                                                                                                                                                                                                                      | `PushKnowsTruth` (a `t3-push` outage longer than the budget drops the thread's last state)                                                                                                                                                                                         |
| `ForgetOnFailure`           | **Host-side fork patch.** A failed publish clears the thread's entry in `publishedStateByThreadRef`, so the next publish always sends.                                                                                                                                                                                                                                                                 | `PushKnowsTruth` (`t3-push` stored the row before the failure. If the thread returns to the last acknowledged phase, the host skips it as unchanged.)                                                                                                                              |
| `NotifyFromPublishedThread` | Without a card, notify from each owed publish's own state (`notificationForPublish`), one per thread for its latest state, in publish order, never for a replay or sweep. Never from the aggregate's first row.                                                                                                                                                                                        | `NoMissedNotification` ("A running, B completes": the first row is A, so nothing rings). Its other harm, re-ringing A's approval on any publish, `NotifyOncePerPhase` now also stops.                                                                                              |
| `HonorLiveActivitiesOff`    | With Live Activities off, end a leftover card (no alert) and send no card updates; alerts go out as notifications.                                                                                                                                                                                                                                                                                     | `CardEndsWhenLiveActivitiesOff` and `OnlyEndWhenBothOff` (the card keeps updating)                                                                                                                                                                                                 |
| `AlertsNeedNotifications`   | Card alerts and notifications only while the stored preferences say notifications are on.                                                                                                                                                                                                                                                                                                              | `SilentWhenNotificationsOff`                                                                                                                                                                                                                                                       |
| `NotifyOncePerPhase`        | Persist, per thread, that its current phase has rung or is ringing, in the same step that writes the send (like `WriteAheadSend`), for a notification and for every thread a card update alerts. A notification for a marked thread is not sent. Clear the mark only when a stored publish changes that thread's phase, or when APNs refuses the send that set it. Keep it after a timeout or a crash. | `NoDuplicateNotification` (without a card, the host republishes an unchanged approval after its 10 s timeout or a title change, and it rings again; with only notifications marking, a card alert followed by Live Activities off rings the same approval again as a notification) |
| `StartupReconcile`          | On boot, queue a replay delivery for every registered phone, from SQLite.                                                                                                                                                                                                                                                                                                                              | `CardEndsWhenLiveActivitiesOff` (the phone turns Live Activities off, `t3-push` stores it and crashes before the queued end runs; nothing queues it again)                                                                                                                         |
| `EndIsFinal`                | From the moment `t3-push` chooses a `live_activity_end`, persisted before the send, the card counts as ended: no card update or card alert is chosen for it again, alerts go out as notifications, and every delivery resends the end, with no alert, until APNs accepts one. Then drop the token.                                                                                                     | `NoMissedNotification` (an end times out but arrives; the next delivery sends an update with an alert to the ended card, and `hasCard` keeps notifications off)                                                                                                                    |
| `ReplayAlertsFromBaseline`  | A replay (registration, startup or sweep) alerts like any delivery: against the persisted sent aggregate. Only a card without a recorded baseline gets no alert.                                                                                                                                                                                                                                       | `NoMissedAlert` (h2's approval is stored, `t3-push` crashes before delivering it, and the startup replay sends it without an alert; the host's retry then finds the card unchanged)                                                                                                |

`EndIsFinal` keeps the token until APNs accepts an end. Dropping it as soon as an end's outcome is unknown breaks `CardShowsTruth`: the grace window passes with no rows, the end times out without reaching the phone, and with no token the empty card stays on screen while h1 runs, until iOS's stale date. Resending only the end covers both outcomes: an end that arrived is resent harmlessly, and one that did not still lands. A refused end is resent too, even if rows arrived since: the card stays ended and the phone gets notifications.

`ReplayAlertsFromBaseline` cannot ring twice: `WriteAheadSend` already wrote every possibly-sent aggregate, ambiguous sends included, before the send, so the replay compares with what may be on the phone. `StartupReconcile` needs it: without it, the startup replay itself swallows any alert stored before the crash.

The alternative to `ReplyAfterDelivery`, answering a publish right after the store, does not pass: owed notifications live in memory, so a crash after the answer loses them even with `StartupReconcile`.

The model also requires these behaviors, which it assumes rather than toggles:

- **A recurring idle sweep.** Like `endIdleLiveActivities`, it ends a card with nothing left to show, on every cron tick (`IdleSweep`). Without it, a send that lands after a crash can leave a "Working" row nobody clears.
- **Restart after the old pod is gone.** Use a `Recreate` rollout. `PushRestarts` requires that APNs has already settled every request the dead process wrote. A newer update from the new pod must not race an older one from the old pod.

## Open findings

None. Every rule holds on every design config.

A finding is a `finding-<name>.cfg` that `check.sh` expects to break its rule on the design, listed in the findings section of `check.sh` with its candidate fix, if any. Leave that rule out of the design configs the finding reaches, so the other rules still get a full check there. When a fix lands, set its constant in every config, put the rule back, add a variant line for the constant, and delete the finding.

## Scope

- **Bounds:** 2 hosts with one thread each, 2 phase changes per thread. Each design config allows one fault of one class. `crash.cfg`, `apns.cfg` and `timeout.cfg` run a phone with a card and notifications on; `notes-crash.cfg`, `notes-apns.cfg` and `notes-timeout.cfg` a phone with Live Activities off and notifications on, so every alert is a push notification; `notes-touches.cfg` the same phone with one title-only change (`MaxTouches`) and one host timeout, the only config with a touch; `modes.cfg` starts in each of the four modes and lets the phone re-register once with any switches, without faults; `modes-crash.cfg` does the same with one crash and one phase change per thread. `all-faults.cfg` allows one of each fault class at once. Every config checks every rule.
- **Phases** are reduced to `none`, `run`, `ask` (approval or input) and `done` (completed or failed). Titles and model names appear only as `ThreadTouches`, a change the host publishes without a phase change. Text changes and the 15 s throttle on changes that only touch them (`MIN_LIVE_ACTIVITY_UPDATE_INTERVAL_MS`) are left out.
- **No clock.** Freshness windows (the 2 min terminal-alert freshness, which `t3-push` checks at send time, so a completion can be dropped after a long APNs retry backoff; the 15 min terminal-row TTL) and the host's 5 s confirmation hold for completions and tombstones (`publishConfirmDeadlines`) are not modeled. The 2 min freshly-armed grace is one `GraceExpires` step.
- **Assumed:** APNs delivers accepted payloads to the phone in acceptance order. A send that fails with an error status reached no one. A host sends one publish at a time (`makeAgentAwarenessPublishWorker`). A re-registration is accepted only while `t3-push` is up. The notification switch is judged when `t3-push` chooses a send: a payload chosen before the phone turned notifications off may still arrive.
- **Not covered:** the phone starting a new card or replacing its activity token (turning Live Activities back on leaves the phone without a card, on notifications), the user dismissing the card, APNs 410 token invalidation, the per-kind switches (`notifyOnApproval` and the rest), which delivery result answers each covered publish (the host only logs it), Android/FCM, and more than one phone. Re-registration with an APNs failure or a host timeout, and re-registration with a crash at 2 phase changes per thread, run only by hand (see Run).

## When to run

Run it when a change touches:

- `apps/server/src/relay/AgentAwarenessRelay.ts`: `publishThreadUnsafe`, `processThreadPublish`, `schedulePublishRetry`, `RELAY_AGENT_ACTIVITY_RETRY_DELAYS_MS`, `makeAgentAwarenessPublishWorker`, or the `publishState` timeout;
- the relay delivery logic `t3-push` reuses (see the coverage table);
- the `t3-push` service in `apps/push`;
- the phone's registration or preference handling (`apps/mobile/src/features/agent-awareness/remoteRegistration.ts`);
- the spec or its configs.

## Run

```sh
scripts/self-hosted/push-model/check.sh            # design configs, each choice turned off, open findings
scripts/self-hosted/push-model/check.sh design     # design configs only
scripts/self-hosted/push-model/check.sh variants   # choices turned off only
scripts/self-hosted/push-model/check.sh findings   # open findings only
scripts/self-hosted/push-model/check.sh deep       # all-faults.cfg: every fault class at once
```

It runs TLC from the repo flake's pinned nixpkgs (`nix shell --inputs-from . nixpkgs#tlaplus`), so no other install is needed. The first run downloads it. The script prints one line per run and the directory holding the full TLC output, and exits non-zero on any unexpected result.

The expected result is `ok` or `open` on every line: every design config passes, every variant breaks the rule listed for it in `check.sh`, and every open finding still breaks its rule (and holds with its candidate fix). Each variant and finding checks only its own rule, because a run can break several rules and TLC's first report would then depend on its worker scheduling.

On a 48-core machine the default run takes about 4 minutes, and the largest config (`crash.cfg`) explores 17.2M distinct states in about 90 seconds. Run the default on every relevant change. Run `deep` before relying on a design change and before moving the sync commit. Before the notification path was added, it passed after 473M distinct states, in about 20 minutes on 32 TLC workers. It has not been run to completion since; with the notification path and `StartupReconcile` expect well over an hour. It catches faults that only combine: the single-fault configs missed a gap that `all-faults.cfg` found (a crash right after the idle sweep ran, with a timed-out send landing later).

Re-registration with an APNs failure or a host timeout, or with a crash at 2 phase changes per thread, is not in any script, because it is slow. To run it, copy `modes.cfg` (or `modes-crash.cfg` with `MaxChanges = 2`) to a scratch directory, set one fault constant to 1, and run TLC on it as `check.sh` does. Before the notification path was added, these runs took 2 to 15 minutes.

## Read a result

Read every result with the `/statechart` skill. Give it the spec and the failing config, or the passing one for a chart. It turns an invariant violation into the shortest path in plain words, and draws a pass as a chart of how the card moves between states.

When a design config fails:

1. Retell the path in this repo's words: "h1's thread finishes, the host publishes, t3-push stores the row and sends, APNs accepts, t3-push crashes before recording, …".
2. Replay it against the code, one step per action, using the coverage table. A path the code cannot take means the model is wrong: fix the model and say what was wrong. A path the code can take is a finding. Report it with the path, and do not weaken a rule or a constant to make it pass. Record it under **Open findings** with a finding config, and leave the rule out of the design configs that reach it.
3. A failure in an action the code does not have yet is a design finding. Change the **Design choices** section along with the spec, and say so.

When a variant line fails ("expected X to break, got pass"), the check has lost its power to catch that design choice being dropped. Find out why before trusting a pass. When a finding line fails, the design may have fixed it: confirm against the code, then follow the steps under **Open findings**.

## Change the verification

When a change is intended (new behavior in the host publisher, the reused relay logic, or `t3-push`):

1. Update the actions in `SelfHostedPush.tla` that describe the changed code, and their rows in the coverage table.
2. Run `check.sh`. If a new design choice guards a rule, add a variant line for it in `check.sh`.
3. Move the sync commit below only after you confirm that the spec describes the code at the new commit.
